3. Make Category / Model / Variant truly catalog-driven
Current MainWindow inserts only the already-selected profile into profile_model. Replace that with catalog-driven population.

4. Make Task profile-driven
A target profile's manifest.supported_tasks is the source of truth.
- H3 retains: T2VA, I2VA, FL2VA, L2VA, Ref2VA.
- Wan 2.2: T2V, I2V.
- LTX-2.3: T2V, I2V.
Prefer showing Task in the target/profile area so it remains visible even when H3-only advanced video controls are hidden.
Do not invent additional tasks in this phase.

5. Preserve H3 controls without forcing them on other profiles
Current PromptSettings/_validate/_ui_block contain H3-specific fields and validation.
Use profile capabilities, not model-name checks.
- If profile.capabilities["legacy_h3_controls"] is true: preserve current Duration 4-15, Camera, Shot, Motion, audio checkboxes, frame notes, references, reference validation, and existing H3 UI block behavior exactly.
- If false: do not validate H3 duration/reference constraints and do not inject unused H3 Camera/Shot/Motion/Audio/Frame/Reference values into the LLM system prompt.
- For non-H3 profiles in this phase, the generated UI settings block only needs Task + Prompt Processing + processing rule. The user describes camera/audio/motion naturally in the request and the profile rules shape them.
- Hide H3-only control groups for profiles where legacy_h3_controls is false.
This is intentionally simple; do not build a generic dynamic UI-schema framework yet.

- The wizard must still require a valid GGUF and inference backend setup.
- Explain in UI/localized text that MiniMax H3 requires the Skill, while other profiles do not.
- H3 generation must keep the existing dependency check and refuse H3 generation with a clear message if the required Skill is missing.
- Wan/LTX generation must not require or fetch the H3 Skill.
- Settings must continue to allow H3 Skill install/update.
- No automatic network request at startup.
